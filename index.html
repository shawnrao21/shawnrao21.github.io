Long-Distance Co-op

  • Python
  • pandas
  • SQL
  • SQLite
  • R
  • JavaScript
  • My friends are spread across different cities now, so most of what Steam calls co-op is useless to us. This finds what we can actually play together. Open it.
  • It separates online co-op from split-screen and LAN, and surfaces Remote Play Together, where one person owns the game and streams it to everyone else.
  • I rank on the lower bound of a Wilson interval, so five perfect reviews do not outrank forty thousand good ones.
  • A Python pipeline I wrote reads six CSVs, about 2.9 million rows, and emits one 260KB file. Everything after that runs in your browser.
  • Cleaning it took longer than building it. pandas dropped 54% of one file to a quoting bug and never raised an error. Playtime came back zero across all 140,077 rows, so I cut that feature. And the genre table stores Counter-Strike in Polish and Dota in Russian, which meant my English filter was quietly deleting the biggest games on Steam.
  • For recommendations I use cosine similarity over tag vectors, weighted by how rare each tag is. Skip the weighting and everything matches on Action and Indie.
  • Terraria returns Starbound. Hades returns Hades II and Binding of Isaac.
  • I also loaded the same six CSVs into SQLite and asked the questions in SQL. Recursive CTEs to split the genre lists, a window function for the rolling average, and Wilson registered as a user-defined function so the ranking happens in the query.
  • Two findings I did not expect. Price peaks at $10 to $20 and falls off above $40. Games shipping in more than fifteen languages average 81.3% against 76.2% for English-only.
  • Then I refit both in R to see whether they survived. The localisation gap shrinks 73% once review count is in the model, because publishers localise games that already sold. The price effect is significant at F = 45.8 and explains 1% of the variance.

Order-Matching Engine

  • C++
  • STL
  • custom priority queue
  • I wrote a C++ engine that matches buy and sell orders the way an exchange does, on price first and then time.
  • It reports a running median price and per-trader totals without ever reading the input twice.
  • My first version never finished the largest test cases. Writing my own priority queue fixed it.
  • I give each equity two heaps, buys in a max-heap and sells in a min-heap, so adding an order and finding its match are both logarithmic rather than linear in the size of the book.
  • The median and the per-trader numbers fall out of that same pass.
  • I profiled before optimising. The matching loop was eating almost everything, so that is where the work went. Reserving capacity up front handled the remainder.
  • Source stays private under course policy. I can walk through the design.

Shell tooling and Git automation

  • C
  • Bash
  • Zsh
  • Git hooks
  • sed
  • POSIX regex
  • I wrote a working Unix shell in C, and a pair of Git hooks that stop me committing things I should not.
  • The pre-commit hook scans staged files for SSH private keys and hard-coded API keys and refuses the commit.
  • Built for EECS 201. I am not publishing the code, since it is coursework other students are still assigned.
  • The shell forks, execs with execvp and waits on the child, handles cd and exit itself because a child process cannot change its parent's directory, and builds its prompt from the environment and the working directory.
  • The pre-commit hook walks the staged file list, matches the OPENSSH markers and a pattern for assigned key literals, and exits non-zero. The commit-msg hook spell-checks through aspell but never blocks a commit, because a spell check should not be able to stop you working.
  • I also wrote a two-line prompt for both zsh and bash that reads branch, dirty files, untracked files, how far ahead or behind the remote, and stash depth, plus the runtime of the last command once it passes two seconds, its exit code if it failed, and a tag when the session is over SSH.
  • Timing that command is the awkward part. Zsh gives you preexec and precmd hooks; bash has neither, so it takes a guarded DEBUG trap and the SECONDS counter to get the same number.
  • GNU and BSD sed disagree on in-place editing and on extended regex flags, so a script written on Linux quietly does the wrong thing on macOS unless you check the platform first.

  • I wrote this page by hand. One file, no framework, no build step, nothing to install.
  • Motion, contrast, colour-vision palette and text size are yours to set, in the corner up there.
  • I tested it from a 320px phone up to desktop at every text size.
  • The chart behind my name is a canvas random walk, drawn at device pixel ratio. It stops the moment it leaves the screen.
  • I used Okabe-Ito for the colour-vision palettes, a published set that holds up under deuteranopia, protanopia and tritanopia.
  • Nothing here leans on colour alone. The current section carries a bar as well as a colour, errors carry an icon and words, and you can force every link to underline.
  • I ran every colour pair through the WCAG contrast formula across all eight theme combinations. Three failed, one of them inside high-contrast mode. Measuring is the only reason I knew.
  • Skip link, visible focus on everything, labels wired to their inputs, errors announced through a live region, and a settings dialog that traps tab and closes on Escape. I checked the whole page works without a mouse.
  • Testing found four bugs that looking never would. The page scrolled sideways at large text. My inputs were under 16px, which makes iOS zoom in and never zoom back. Some tap targets sat below the 24px minimum. Padding written in rem ate the viewport at 150%.
  • It respects prefers-reduced-motion by default, and the panel overrides that either direction.
